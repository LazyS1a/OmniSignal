2026-11-06。仅本地离线开发，未调用真实素材网站、模型、SSH、GitHub 或线上发布接口。测试内容全部为程序生成的合成案例，不代表真实素材许可、模型质量或下游接收成功。

## 已接入的路径

- `knowledge/snapshot_v3.py` 生成 recipient 绑定的完整目录快照。保留原案例、证据、内容哈希和 v2 用途依据；v3 不新增授权。
- `workbench/publishing.py` 在显式启用后接入正常工作台发布事务。原冻结批次的签名前策略复查、恢复身份、未确认接收状态继续保留。
- `workbench/feed.py` 在已有 library scoped feed 下增加 `/snapshots/latest` 和 `/snapshots/releases/{release_id}/manifest|parts/{sha}|objects/{sha}`，沿用下游令牌及精确库范围。仅可读取被该完整版本引用且哈希验证通过的文件。
- v3 数据保存在已选库根的 `v3/`。其 latest、release manifest 与旧版分离；不覆盖 v1/v2 latest。

## 分片和复用

目录按 `sha256(case_id)` 的前两位分组。某组超过目标 500 条或 8 MiB 时，仅沿该前缀递归细分，最深 8 位。每片硬上限 2000 条，根清单最多 4096 个不重叠分片、实际文件最多 1 MiB；全目录最多 100000 条。超限明确停止，不能通过截断目录来伪装完整。

分片和图片均按实际字节 SHA-256 存一次。后续目录引用相同 SHA 时不改写历史文件；完整目录的每个 release 仅保存根清单。一次构建仅保留一个序列化分片和一个图片对象的字节，不把全库图片放进内存。当前案例元数据仍作为受 100000 条上限约束的完整列表处理，尚不能宣称元数据内存与目录规模无关。

历史版本及撤回记录不自动删除。私有 SQLite 索引保留所有已知案例的最高 revision/content_hash，包括曾从目录中暂时消失的案例；初次迁移会验证旧发布记录并继承高水位。重启会校验并补记已生成但未登记完成的不可变 manifest，再恢复最新指针。旧版本重放不能回退新指针。

## 开关与有限容量

`OMNISIGNAL_SNAPSHOT_V3_ENABLED` 默认 `false`，只接受 `true/false/1/0`。没有确认接收端已支持前不能打开；本次未变更运行配置。关闭开关后，已签名 v3 库存仍用于状态、未接收额度和撤回核对；新增发布明确停止，不能自动降级成旧版并遗漏历史。

`OMNISIGNAL_SNAPSHOT_V3_MAX_IMAGE_BYTES` 默认 **2 GiB 完整目录图片总量**，不是每日增量额度；允许明确配置正整数，硬上限 100 GiB。

`OMNISIGNAL_SNAPSHOT_V3_MAX_RETAINED_BYTES` 是独立的 **4 GiB 默认持久内容预算**，同样只能显式配置为正整数且不超过 100 GiB。它统计 `v3/objects`、`v3/parts`、`v3/releases` 中所有实际文件字节，包括旧快照保留和中断后尚未引用的缓存；不能只看最新目录而漏掉历史增长。构建第一遍只规划对象、分片和根清单的准确新增字节，通过持久预算与磁盘检查后才写 CAS；签名前再核对最终库存和含 LF 的 manifest 字节。超限不签名、不更新 latest、不自动清理历史。

私有 SQLite/日志、锁文件、临时准备目录及旧 v1/v2 数据并非上述 v3 不可变内容，不把该预算冒充整个磁盘上限；真实磁盘余量另外覆盖计划新增内容和元数据预留，实际写入失败也保留旧指针。之后必须依据整机磁盘余量、B 的暂存能力和费用配置合适预算，不自动扩大。

若已有更高版本的完整 manifest，但前次 latest 切换尚未恢复，必须先按原冻结请求重试，新批次不能从旧指针继续合并并遗漏已签名内容。独立旧版写入者在 v3 之后推进旧协议时，新的 v3 发布要求显式重新定基；跨协议相同 sequence 冲突也明确拒绝。

图片保持原单图 20 MiB、4000 万像素限制；必须完整解码，并验证 MIME、尺寸、哈希，动画图不能作为静态对象混入。旧撤回通道继续使用独立签名，完整目录声明最低撤回水位。累计撤回文件长期分页仍是单独后续项，不能声称本次已解决。
