# 试点采集：成功项目数与检查次数

工作台每次运行会按来源列表顺序跳过已入库项目，再检查新候选。列表中可能有不支持的媒体或不完整页面，不能让前两个失败候选占完全部采集机会。

## 配置

`OMNISIGNAL_WORKBENCH_COLLECTION_PROJECT_LIMIT` 控制**每个采集计划单轮最多成功获取的项目数**：

- 缺省为 `2`，保留原来的成功项目数量。
- 合法值为严格的十进制字符串 `1` 至 `10`。
- `0`、负数、`11` 及以上、`unlimited`、小数、空串、前导零、带符号或空格等非法值均回退为 `2`。
- 每轮候选尝试上限为 `max(6, 项目上限 × 3)`，最多检查 30 个新候选，不会无限跳过失败页面。
- 每项目仍最多取 3 张合格静态图。因此配置 `10` 的理论上限是每轮 30 张，实际受来源、已有项目、图片质量和请求预算约束。

这是工作台服务级配置，对各已启用采集计划分别生效。修改后需要让服务进程读取新的部署环境；仅在宿主机环境文件添加键，而 Compose 没有传入容器时，不会生效。

## 保持的限制

计划原有日 HTTP 请求预算、robots、域名白名单、请求间隔、响应大小、图片质量、暂停和停止逻辑均保持。新增图片仍进入待处理，分类未确定，用途权限保持未知，不自动送模型或发布。

候选正文的解析失败会跳过并继续检查后面的候选；网络、robots、403、429 或访问验证错误仍停止本来源运行，不能为了凑满数量跨过访问限制。视频 iframe 不会被改成静态广告图，原解析器仍拒绝不支持的媒体。

## 首周解释口径

“30 张”是理想图片上限，不是产量保证，也不是 30 个独立项目。同一包装案例取 3 张图时，10 个项目才对应 30 张图片。日模型分析次数和采集请求预算是不同配置，不会互相替代。

即使成功获取若干图片，遇到其它不完整候选后，该轮仍可能标记为 `partial`；应同时查看实际新增数，不能将 `partial` 一律理解成 0 入库。

本次修改只分离成功数与尝试数，没有增加失败候选持久退避、逐 URL 诊断或分页游标。首屏候选全部已知时仍可能没有新素材，需要单独评估分页或其它来源。

## 离线验收

新增测试采用合成 HTML 和图片：前三项为视频而后方静态图能够入库；全失败候选有界；默认仍最多两个成功项目；合法 `1/2/5/10` 与非法边界；十项目模式仍受预算、权限和暂停约束；访问限制不被当作普通解析失败跳过。

真实生产采集应在部署后经正常工作台 API 小范围运行，并核对新增项目数、新图片数、请求数及待处理权限。配置 `10` 不代表此步骤已经通过。
