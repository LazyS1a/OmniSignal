# Omni 设计分析 Skill 改造计划

日期：2026-11-02。状态：已获批准，开发进行中；实际验证与部署结果以本轮交付日志为准。

## 本轮授权变更（2026-11-02）

用户明确要求由 AI 分析和发布，尽量减少人工审核。本节覆盖下文原计划中“保持 auto_publish=false”“正常素材必须人工审核”的旧安排：正常素材由模型分析、证据与版本校验、AI 质量复核后自动收录；已具备展示和传输用途记录的素材自动生成签名发布包。旧用途记录 unknown 不由模型改成 allowed，已撤回的素材继续排除，异常自动隔离。人工只承担可选纠正和不能自动确定的例外处理。AI 审核不会记成人工完成。

开发分支：`feat/omni-design-analysis-skills`。正常调度仍为每日采集目标 100 张、主分析目标 120 张；新版先灰度到每日 20 张，既有结果与历史失败不自动重跑。评测优先使用自有合成素材验证技术和证据规则，真实内容质量仍需独立评估；三天自然观察不能用一次测试代替。旧协议消费端先保持兼容，新灵感卡可投影到已有设计分析字段。

目标：让采集到的图片得到更具体的设计分析，用可核对的依据辅助收录，再形成 DeepFlare 能检索和解释的灵感案例。

实施主线：版本与证据契约 → 三类专项分析 → 内容复核 → 灵感卡与待处理分组 → 小样本评测 → 小范围运行 → DeepFlare 接收与展示。

## 2. Lovart 资料如何转成我们的规则

原始资料作为设计方法和证据使用；其中的工具调用、系统提示和审批指令不作为本项目的执行授权。

| 本地材料 | 可借鉴部分 | 对 Omni 的改写 |
| --- | --- | --- |
| `all_skills_feed.json` 的包装模板、`SKILLS_DESIGN_16.md` 包装章节 | 主展示面、品牌与产品信息层级、系列变化 | 分析已有图片中可见的组织方式，缺失的背面、结构和工艺保持未知 |
| 品牌视觉方向板、VI 模板 | 配色、字体、图形和应用的一致性 | 记录具体视觉规则与可复用方法；单张图片不证明整个品牌系统一致 |
| `skills_md/Meta广告创意.md` | 参考图角色、广告主张、行动引导、事实依据 | 分析图片承担的沟通任务，区分可观察内容与效果推断 |
| Amazon 卖点证据图模板 | 产品事实与卖点证据关联 | 写明卖点来源；缺少商品资料时，不补造性能、认证或转化效果 |
| Skill 版本、按需加载、具体失败项、产物关联方法 | 专项规则复用与追溯 | 固定本地规则版本，按图片类型应用，错误定位到字段或依据 |

资料边界：生成作品的模板需改写为分析已有作品的规则；“产品广告”卡片实际是广告片生成，不作为静态图分析能力。部分 references 内容在报告中属于交互反推，不能当成已取得的完整后端代码。平台规格如要进入正式生成/合规检查，应另核对当前官方来源；首期不硬套报告中的投放尺寸规范。

## 3. 阶段与待做清单

### 阶段 0：冻结输入、状态和版本契约

- [ ] 盘点现有分析结果、分类字典、审核状态、缓存身份和 Nova 接收协议。
- [ ] 定义三类 Skill 的适用范围、通用兜底、规则版本、输出版本与必要证据。
- [ ] 固定输入绑定：素材 ID、素材版本、原图哈希、来源资料版本、模型身份、Skill/提示词/校验规则版本。
- [ ] 新版缓存身份包含上述版本；规则变化产生新身份，旧结果仍保留原版本，不冒充升级结果。
- [ ] 明确一张图同时属于包装和广告时的优先规则：首期以主要媒介确定主规则，广告传播目的作为补充维度；冲突不确定时走通用分析并记录待确认项。
- [ ] 给新结果预留独立的分析详情记录与旧八字段投影；不直接在严格校验的旧结果对象中随意增加字段。
- [ ] 确认任务状态与恢复规则：读取同一任务回执，未确认提交不重发；变更原图/关键输入使旧结果失效；失败不自动重试。

交付：输入/输出契约、状态转换表、Skill 路由表、旧协议兼容说明。

通过条件：版本变化不会误命中旧缓存，历史记录可读，重复提交、并发编辑、撤回和失效结果都有确定行为。

### 阶段 1：三类专项分析与通用兜底

- [ ] 建立三个自有规则包：`packaging-analysis`、`brand-visual-analysis`、`static-ad-analysis`；这些名称为拟建模块，当前尚不存在。
- [ ] 包装规则覆盖主展示面、阅读顺序、识别锚点、可见系列变化、可借鉴方法与未知项。
- [ ] 品牌视觉规则覆盖标志/字体/配色/图形的角色和关系，区分品牌事实、视觉风格与模型推断。
- [ ] 静态广告规则覆盖主张、主视觉、卖点依据、行动引导、信息密度和可读性；缺少效果数据不评价实际投放表现。
- [ ] 未知、混合或不适用内容走 `general-analysis`，保留“无法确认”；不按来源网站直接判定图片类别。
- [ ] 路由优先使用与当前原图绑定、可核对的既有分类。未知新图使用带三类精简分支的统一入口，在同一次调用中返回所选类型、依据和对应分析；服务端检查路由与输出是否一致，无法判断时返回通用结果。首期不为了路由给每张图固定增加一次模型调用，也不让全部新图继续落回原来的通用八项套话。
- [ ] 主分析仍使用现有千问接口，每张图片每次任务只调用一次；加载适用的必要规则，记录实际使用的规则和输出长度限制。
- [ ] 分别保存图像观察、来源陈述、分析推断和未知项；推断附具体依据，不用未经校准的模型分数代替真实性判断。

交付：三个专项规则、通用规则、加载与路由实现、合成输入输出夹具。

通过条件：相同类型输出可比较，不同类型有明确关注点；无法确认的字段不会为了凑齐文字被编造。

### 阶段 2：内容复核与具体失败原因

- [ ] 保留现有身份、权限、哈希、版本、字段和任务完成检查。
- [ ] 添加内容检查：字段互相矛盾、空泛套话、缺少依据的具体品牌/材料/效果描述、分析与原图不对应。
- [ ] 区分阻断错误与局部未知。原图不对应、关键身份矛盾阻断采纳；某项工艺不可见等局部未知可保留有用分析，明确标注限制。
- [ ] 输出结构化问题：问题类型、对应字段、依据、建议动作。逐项规则先记录原因，再由程序决定状态，不让模型直接设置权限或人工审核身份。
- [ ] 对存在语义疑点的结果设计第二次看图复核，输入为原图、冻结的分析结果和有限检查项；同模型第二次调用仍有共同偏差，保留人工判定入口。
- [ ] 为第二次复核设置独立任务身份、次数上限和用量记录；不循环自我修改，不把网络失败转成内容失败。
- [ ] 首期默认先输出复核建议；通过对照验收前，不用新语义结论直接改变线上收录状态。

交付：质检规则、原因码、复核结果结构、人工处理入口及调用计数。

通过条件：能说明“哪里有问题、凭什么、下一步做什么”；不会用字段齐全或模型自评高分冒充真实质量合格。

### 阶段 3：灵感卡与批量处理体验

- [ ] 从同一次分析结果整理灵感卡，默认不增加一次独立模型调用。
- [ ] 卡片包含：设计任务、视觉方法、图上/来源依据、适用场景、使用限制，以及原图与来源引用。
- [ ] 绑定生成该卡片的原图、分析任务、Skill 版本及审核来源；没有依据的字段保留为空或未知。
- [ ] 新卡片先作为分析建议展示，与已经审核的版本分开；采纳时沿用现有版本检查和审核记录。
- [ ] 待处理区增加原因筛选：等待分析、技术失败、分析需补充、分类待确认、版本失效。
- [ ] 批量界面同时展示共性问题和逐项例外；一键收录不自动把 AI 内容变成人工逐项审核。
- [ ] 手机端核对按钮、理由和异常项的可见性，保留原单张详情和批量收录操作。

交付：本地灵感卡、详情展示、原因筛选、批量处理结果展示。

通过条件：用户能从卡片说出可借鉴的方法，并能回到对应原图/依据；每项审核身份、版本和用途状态清楚。

### 阶段 4：小样本对照与验收

- [ ] 选 20 张已具备 AI 分析依据的素材，包装/品牌视觉/静态广告/模糊或混合内容各 5 张；记录样本 ID、哈希、版本与使用范围，私有保存。
- [ ] 每类 3 张用于调整规则、2 张用于保留测试，共 12 张开发样本和 8 张保留样本。若缺少类型，不拿同质素材凑数，报告覆盖缺口。
- [ ] 比较旧规则与新规则；只有图片、输入和模型身份可比的旧结果才能复用为基线。
- [ ] 需要重跑的基线在隔离评测任务中执行，不修改线上旧任务或清空历史失败；本轮对照主分析最多 40 次，疑点复核最多 5 次，总计上限 45 次。可复用旧结果时相应减少。
- [ ] 该上限是后续评测的建议预算，本次不启动调用。使用量按真实任务计数；无实际计费信息时不虚构人民币成本。
- [ ] 输出图片相同、顺序打乱的对照表，记录分类正确性、分析具体性、无依据断言、误收/漏收、耗时和可取得的 token/计费量。
- [ ] 人工质量验收由帅帅或指定审核人确认；助手评分只算辅助评估。未取得人工结论时，质量验收标为待完成。
- [ ] 运行有意义的回归：错原图、版本变更、规则升级、截断/拒答、部分字段未知、重复提交、响应丢失、权限不足、撤回、旧协议读取和模型调用上限。

拟定小范围运行门槛：

| 指标 | 首次通过条件 |
| --- | --- |
| 保留样本分类 | 8 张中至少 7 张正确；正确保留“未知”可计正确，硬猜不计 |
| 保留样本分析价值 | 至少 6/8 张被人工判为比旧规则更具体、更可用；其余无严重退步 |
| 严重无依据断言 | 20 张中发现的明确品牌/效果/材料等虚构全部解决；不把修正后的开发集成绩当保留集成绩 |
| 不确定内容 | 不靠补造内容强行通过，局部未知有清楚解释 |
| 工程保全 | 无重复计费提交、无权限提升、无真实素材改写或自动发布，现有收录/撤回回归通过 |
| 成本与延迟 | 报告主分析/复核各自调用次数和延迟；拿到基线后再确定可接受阈值 |

20 张只能作为首轮进入小范围运行的依据，不代表长期准确率。保留样本被用于修改规则后，下一轮需换新的保留样本。

### 阶段 5：小范围上线、观察与回退

- [ ] 提交可审查的改动，完成相关回归、构建和独立复核；上线前刷新服务器运行状态与配置。
- [ ] 增加功能开关和版本选择；旧分析路径保留。新增数据结构须向后兼容，旧版本回退后能够忽略新记录。
- [ ] 首轮在现有每天最多 120 张主分析中选不超过 20 张采用新规则，其余沿用旧规则，同一素材不重复安排两次主分析。
- [ ] 新规则的复核结论先只记录、展示供核对，不直接影响自动收录；进入这组新分析的素材暂留待处理，避免旧规则绕过新结论先自动采纳。其余素材保留原流程。
- [ ] 小范围运行期间每天二次语义复核最多 5 次，单列为额外调用，不隐藏在“120 张”指标里；这是拟定新增预算，实施时显式配置并计数。
- [ ] 连续观察至少 3 个自然日，按来源和类别记录供给、完成、异常、人工判断及额外用量。没有足够样本或人工结论时不因时间到就扩大。
- [ ] 验收后分开决定“扩大新分析覆盖”和“让新质检影响自动收录”；不自动把两者同时打开。
- [ ] 保持 `auto_publish=false`，展示与传输仍逐批确认。
- [ ] 出现重复提交、关键幻觉、版本串用、明显质量退步或调用预算异常时关闭新功能；保留新旧记录，不用旧数据库备份覆盖当前数据。

交付：实际运行报告、指标对比、配置开关、镜像与数据保全核对、回退步骤。

### 阶段 6：DeepFlare 消费端接入

- [ ] 在 Omni 第一版稳定后，核对 DeepFlare 当前接收分支、发布协议及已有本地知识副本。

- [ ] DeepFlare 按用户设计任务、媒介和可复用方法检索，展示推荐原因；品牌信息不足时不给出确定的品牌匹配结论。

- [ ] 用自有或明确获准展示/传输的测试素材验证发布、拉取、签名/哈希、版本切换、检索、引用和撤回。
- [ ] 分别记录 A 端发布成功、B 端接收成功、用户端可见；以接收回执和实际引用为验收依据。

交付：接收端兼容实现、灵感卡展示、检索样例和真实技术链路回执。品牌专属排序与生成方向板列入后续优化，不强塞进第一版。

## 4. 建议改动位置与协作顺序

| 工作块 | 主要位置 | 依赖 |
| --- | --- | --- |
| 契约与路由 | `src/omnisignal/workbench/` 下新增分析规则与版本模块；规则内容独立目录 | 最先冻结输入、输出、状态和缓存身份 |
| 模型接入 | `analysis.py`；检查 `nova_analysis.py` 的兼容调用 | 使用已冻结的规则接口，保持当前千问通道 |
| 复核与自动流程 | `review.py`、`auto_editorial.py`、`daily_pilot.py` | 区分分析成功、复核结论与采纳状态 |
| 灵感卡与界面 | `Analysis.tsx`、`ReviewedAnalysis.tsx`、待处理列表与批量界面 | 使用固定数据契约，前期可用合成数据并行开发 |
| 发布与接收 | Omni 发布模块；后续 DeepFlare 接收端 | 旧协议兼容先完成，再独立接收验收 |
| 评测与部署 | 隔离评测工具、相关测试、部署辅助目录 | 质量报告与工程回归通过后推进 |

后续若并行开发，建议分为“规则与分析”“复核与版本”“前端与评测”三条线，由主代理统一契约和集成。不同代理避免同时改同一核心文件；部署核验在代码冻结后进行。
